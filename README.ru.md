# ai-agent-rules

Постоянные правила одного человека для ИИ-агентов, общие для всех инструментов и всех
репозиториев машины. Не только текстом: то, что можно проверять механически, проверяют
хуки, а то, что нужно лишь в конкретный момент, приезжает скиллами.

Это ровно то, что иначе повторяешь в чате каждый день и копируешь из проекта в проект,
пока копии не разойдутся: коммит только по просьбе, наружу ничего без одобрения,
вопросы задаются на этапе плана, файл правил не журнал работ.

**Что стоит знать до установки.** Это лезет во внутреннюю конфигурацию обоих агентов:
регистрации хуков вливаются в `~/.claude/settings.json` и `~/.codex/hooks.json`, симлинки
появляются в обоих их деревьях, три строки уходят в машинный git ignore. Всё, что
заменяется, сначала сохраняется рядом, трогаются только записи, ведущие в этот клон, а
`scripts/uninstall.sh` снимает всё обратно по группам. И всё же ни один из этих файлов не
является документированным интерфейсом: их вид меняется между версиями инструментов,
поэтому после того, как любой из них обновился, запусти `scripts/doctor.sh` и прочитай
вывод, прежде чем считать, что хуки по-прежнему срабатывают.

## Что здесь лежит

| | |
| --- | --- |
| [`AGENTS.md`](AGENTS.md) | сами правила, по строке на каждое. Канон; `AGENTS.ru.md` — русская копия |
| [`docs/RATIONALE.ru.md`](docs/RATIONALE.ru.md) | почему каждое правило существует. Агент это не читает, читает человек |
| [`docs/mechanisms.ru.md`](docs/mechanisms.ru.md) | что механизмы делают на самом деле, замеренное, включая шесть мест, где названия врут |
| `hooks/` | девять хуков: семь запрещают или напоминают по наблюдаемому триггеру, два несут состояния, о которых должен услышать скилл |
| `skills/` | восемь скиллов, которые ставятся глобально — plan, handover, context-snapshot, audit, translate, rules-edit, new-repo, pass-secrets — и `rules-install`, который остаётся здесь |
| `registry/` | регистрация хуков для каждого инструмента, раскладывает `install.sh` |
| `scripts/doctor.sh` | что установлено, а чего не хватает. Ничего не меняет |
| `scripts/uninstall.sh` | снимает всё обратно, по группам, с вопросом перед каждой |
| `templates/` | форма плана работ |

## Как устроено

Claude Code читает `~/.claude/CLAUDE.md`, Codex читает `~/.codex/AGENTS.md`. Оба файла
симлинки в клон этого репозитория, поэтому правится один файл, а видят его оба
инструмента. Правка действует с момента сохранения.

Строгость правила помечена. **[hard]** репозиторий переопределить не может.
**[default]** молча уступает правилу проекта, благодаря чему файл применим и в
репозиториях, где свои правила уже есть.

Три уровня надёжности, и файл говорит, что к какому относится. Хук исполняет харнесс,
поэтому он держится независимо от того, сколько сессия уже идёт. Скилл приезжает в
момент работы. Всегда загруженный текст самый слабый из трёх и слабеет по мере роста
сессии: замер, из которого это следует, и из которого выросла вся раскладка, лежит в
[`docs/mechanisms.ru.md`](docs/mechanisms.ru.md).

Один хук стоит назвать отдельно. `session-start.sh` определяет, в каком из восьми
видов репозитория ты находишься: локальный, свой публичный или приватный, рабочий с
правилами или без, чужой с правилами или без, и говорит, что из этого следует. Чтобы
разница между «пушить свободно» и «сюда не пушить никогда» не была абзацем, который
кто-то должен помнить. Какие хосты и аккаунты свои — личное, поэтому лежит в файле вне
git, который создаёт `install.sh`.

Тот же хук подкладывает Codex содержимое `AGENTS.local.md`, потому что Codex этот файл
не читает, а настройка, которая выглядела заменой, ею не оказалась.

## Установка

```bash
git clone git@github.com:svesh87/ai-agent-rules.git
cd ai-agent-rules
./install.sh
```

Или, открыв клон агентом, попросить его поставить правила. Скилл `rules-install` уже
подключён внутри этого репозитория, поэтому вызывается сразу после клона, когда ещё ничего
не установлено. Он читает `scripts/doctor.sh`, спрашивает то, что скрипту угадывать нельзя
(какие аккаунты на форджах и какие git-идентичности твои, какой хост рабочий), и запускает
установщик. Ответы уходят в файл вне git, потому что классификатору они нужны, а
репозиторий публичный.

`scripts/doctor.sh` сам по себе говорит, что на месте, а чего нет, и ничего не меняет.

Скрипт сначала прогоняет selftest хуков и, если он падает, не ставит ничего. Дальше
раскладывает симлинки на файл правил и на каждый скилл в оба инструмента, вливает
регистрацию хуков в `~/.claude/settings.json` и `~/.codex/hooks.json`, не задевая уже
стоящие там чужие хуки, создаёт профиль классификатора и добавляет `tmp/`, `*.local.md`
и `*.local/` в машинный git ignore. Root ему не нужен, всё, что заменяет, он сохраняет
рядом, и повторный запуск безопасен.

В Codex хукам надо один раз дать доверие в настройках хуков, иначе они не выполняются.
В VS Code это делается в настройках Codex; в интерфейсах, где есть команда `/hooks`, она
открывает те же настройки.

Только правила, без хуков и скиллов:

```bash
ln -sfn "$PWD/AGENTS.md" ~/.claude/CLAUDE.md
ln -sfn "$PWD/AGENTS.md" ~/.codex/AGENTS.md
printf 'tmp/\n*.local.md\n*.local/\n' >> ~/.config/git/ignore
```

Где лежит клон — дело твоё; путь прописан и в симлинках, и в зарегистрированных
командах хуков, поэтому после переноса надо запустить `install.sh` снова.

## Если хук мешает

Он страховка, а не приговор, и может быть неправ. Два свойства проверяет
`hooks/selftest.sh` до того, как что-то встанет на место: редактор внутри рабочего
дерева не блокируется никогда, а payload, который хук не смог разобрать, пропускается,
а не запрещается. Так путь починить хук остаётся открытым.

Выключить все сразу:

```bash
claude --settings '{"disableAllHooks":true}'      # Claude Code
# Codex: снять доверие в настройках хуков (/hooks, где доступно) или убрать записи
# из ~/.codex/hooks.json
```

`hooks/selftest.sh` сам по себе говорит, ведут ли они себя как задумано. Лог лежит в
`~/.cache/agent-rules/hooks.log`; в репозиторий не пишется ничего.

## Обновление

```bash
git pull
./install.sh
```

Для правил и скиллов достаточно `git pull`, потому что симлинки указывают в рабочее
дерево. Установщик нужен снова, когда добавились или переименовались хуки.

Изменение правила — это правка, коммит и пуш, в этом порядке, и правка действует с
момента сохранения файла. Правила требуют ещё одного шага перед этим: сверить новый
пункт со всем файлом, а не с соседями по разделу, потому что стоящие внимания
противоречия — это противоречия между далёкими разделами.

## Как снять всё обратно

```bash
scripts/uninstall.sh              # спрашивает перед каждой группой
scripts/uninstall.sh --dry-run    # печатает, что ушло бы, и ничего не трогает
```

Четыре группы, каждая отдельным вопросом, и перед вопросом сказано, чем он обойдётся:
симлинки и регистрации хуков, кэш вместе с логом срабатываний, три строки в машинном git
ignore и профиль классификатора. Последние две стоит прочитать прежде, чем отвечать: строки
в ignore мог положить не этот установщик, а профиль личный и набран руками, поэтому
переустановка вернёт пустой шаблон, а не твои ответы.

Удаляется только то, что поставил этот клон, и узнаётся оно по тому, куда указывает симлинк
или команда хука, поэтому чужие хуки и скиллы остаются на месте. Бэкапы, сделанные
установщиком, не трогаются никогда: это единственный путь назад к конфигурации, пришедшей
не отсюда.

## Как сделать своим

Форкнуть и начать с того, что явно личное:

- язык чата, в первой строке раздела **До того, как что-то делать**;
- аппаратный ключ, который определяет правила про коммиты: подпись требует физического
  касания, поэтому коммит никогда не предлагается без просьбы и повторяется не больше
  одного раза;
- профиль, который читает классификатор репозиториев: его заполняешь ты, и в git он не
  попадает никогда.

Остальное не столько личное, сколько пристрастное, и его стоит прочитать прежде, чем
удалять. Правила про `tmp/`, про аудиты разных моделей и про дублирование между этим
файлом и правилами проекта существуют потому, что каждое из них уже один раз оплачено.
